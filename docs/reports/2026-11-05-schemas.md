# T2 契約：schemas と検証

## 要旨

- plan §5 の全 JSON の形を `schemas/` に書き、形の検証と、参照先の実在の検証ができるようにした
- 役の出力の中身の検査（存在しない item を指す、など）は、それぞれの役の PR（T4〜T6）で足す
- 判断をお願いしたいことは 1 件（#2 のマージの指示）

## 何を狙って、どういう順で作ったか

T4 以降の役とスクリプトは、すべてこの契約の上に載る。先に固めることで、役の出力が壊れていても保存の前に止まる。#2 がマージ前なので、CI の修正を含むよう #2 の上に積んだ。

## 到達点

| 誰が | 何をする | 結果 |
| --- | --- | --- |
| スクリプト | 役の出力を受け取る | 形が違えば保存の前に止まる |
| スクリプト | 型の帳面を読む | 型に録音の裏付けの無い項目、演者が確かめていない札、指摘の残る札があると止まる |
| 開発者 | 契約を破った JSON を作る | どの参照が壊れたかが分かる。値（演者の言葉）はエラー文に出ない |

## 主な判断と、その理由

| 判断 | 理由 |
| --- | --- |
| 手で付けた反応の順位は、書かなければ空にした | 偽の順位を入れると「回収の中で下位 4 分の 1」の判定が汚れる。plan の「未検出を反応なしと扱わない」と同じ考え |
| 区間が全部空の項目は、schema を緩めずに根拠の検証で落とす | 引用が空の項目を正本に入れない。落とした数を数える（T4 でテストする） |
| 札の検査を「写しであること」から「過不足なく場面順」まで広げた | 札は見せ場の 4 番目。出すべき札の漏れと、指摘の残る札を止める |
| `source.approved` と `item.approved` は両方残した | 前者は演者の言葉の確認、後者は札に出す承認で意味が違う。後者だけ立つ食い違いを止める |
| 演者の追記の `basis` は `heard` のまま | 「本人が言った」ことを示す。plan の item の形を変えない |
