読むのは**承認者**（部長への報告のつもりで）。「何を狙って、どう判断し、何ができて、何を決めてほしいか」が先。技術の詳細は付録に回す。推測ではなく実行した結果を載せる。

## 置き場
- 本文：`docs/reports/YYYY-MM-DD-<slug>.md`
- 画像：`docs/reports/img/YYYY-MM-DD-<slug>-<n>.png`。本文から相対パスで参照
- PR 本文からリンクする

## 章立て（この順。無い章は省く）
1. **要旨**：3行。何ができたか、何が残るか、判断をお願いしたいことの数
2. **何を狙って、どういう順で作ったか**：背景（締切・審査基準）と、順序の理由
3. **到達点（できるようになったこと）**：技術用語を避けて、誰が何をするかの表。実際の出力例を1つ（「これは設計どおり」の説明を添える）
4. **主な判断と、その理由**：選択肢を比べた結果と根拠。審査基準や現場の使い方に結びつける
5. **数字（実測）**：値と「意味」の2列。推定は書かない
6. **判断・用意をお願いしたいこと**：番号付き、具体的に（何を、いつまでに、無いとどうなるか）
7. **リスク**：リスク・現状・対策の表。Issue 番号つき
8. **次の計画**：日付つき
9. **付録：技術的な記録**：PR・日誌・ログへのリンク、スクショ、注記（合意からの逸脱があれば正直に）

## 書き方
- 結論から。1段落3行以内。比喩より数字
- 「なぜそうしたか」を必ず添える（読む人は承認者で、技術を再現する人ではない）
- 想定外・失敗・合意からの逸脱は隠さず「注記」に

## スクショの撮り方
- Web 画面（viewer など）：
  ```
  uv run python -m http.server -d . 8000 &  # 終わったら kill
  "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
    --window-size=1280,900 --screenshot=docs/reports/img/<name>.png "http://localhost:8000/viewer/?run=../out/view"
  ```
- GitHub の PR・コメント：`gh pr view <N> --comments` のテキストを引用
- 画面に秘密・個人情報・所属・演者のデータが映らないこと（公開 repo に入る）。スクショはダミーのデータで撮る

## 書かないこと
- 演者のデータ（型、ノート、速記、文字起こし、演目の中身）、名前
- 推定の数字、所属、秘密
